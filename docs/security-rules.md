# 施工規範：安全與邏輯

網站、App 與資料庫的每一次修改都照這份規範做。2026 年 10 月第一次整體檢查（1.5.0）找到的問題，都整理成下面的規則；之後新增功能前先對一遍，做完再對一遍。

## 權限一律在伺服器檢查

- 所有資料表開 RLS，預設不開放任何權限；使用者只能透過 RPC（`security definer`、`set search_path = public`）讀寫
- 每支 RPC 都要 `revoke execute ... from public, anon`，只 `grant` 給需要的角色
- 前端與 App 的權限判斷只用來隱藏按鈕，真正的檢查在 RPC 裡；新增一個操作時先寫 RPC 的檢查，再做畫面
- 使用者可以直接 `update` 的欄位越少越好。時間（建立、最後登入）、圖片網址這類由後端決定的欄位，用觸發器保護：使用者送來的值直接忽略、保留舊值，不要報錯，這樣舊版 App 不會壞掉
- API route 驗證 token 要用 `auth.getUser(token)` 向伺服器確認，不能只解開 JWT；用 service role 之前，先用使用者身分呼叫對應的權限 RPC
- 檔案開頭加 `import 'server-only'` 的模組才能碰 service role

## 階層

- 群組與網站都是同一套規則：只能管理身分組比自己低的人與身分組，只能開自己擁有的權限
- 同一個等級的人不能互相管理，只有擁有者可以（群組擁有者、網站擁有者）；沒有人能管理擁有者
- 網站的「管理員」「管理所有群組」在每個群組都視同群組擁有者，可以看所有驗證碼。這是刻意的設計，不是漏洞
- 新增權限位元時，資料庫（`init.sql` 的全部權限值與遮罩）、網站 `src/lib/permissions/bits.ts`、App、`docs/groups-and-permissions.md` 要一起改
- 網站與群組的「全部權限」不一樣（目前 `SITE_ALL = 2047`、`GROUP_ALL = 1023`）；改其中一邊時逐一確認每個出現的地方屬於哪一邊，不要整批取代

## 加入群組的每個入口都要檢查

- 邀請連結、Email／@ID 邀請、接受邀請、直接加入成員，都要檢查：封鎖名單、群組是否加密
- 判斷群組狀態前，先用 `for share` 鎖住群組那一列（不要加 `where encrypted` 之類的條件），避免同時開啟加密時被搶進去
- 踢人只會移除當下的成員，要擋人回來用封鎖名單

## 紀錄要留，敏感資料要遮

- 刪除帳戶時，邀請連結「撤銷」而不是刪除，並寫一筆操作紀錄；操作紀錄一律保留
- 保留期限：登入紀錄一年（刪除帳戶後也一樣）、加密密碼的託管密文在帳戶存在期間保留，刪除帳戶後再一年
- 驗證碼本身刪除就是真的刪除，不另外保留
- 群組的操作紀錄給一般成員看時，電子郵件只給看得到 email 的人，邀請碼只顯示前 4 碼；網站後台看完整資料
- 網站管理員靠網站權限「查看」使用者或群組的資料（金鑰、2FA）時要留紀錄，但只在後台看得到：不列進群組的操作紀錄與使用者自己的紀錄。之後新增同類的查看紀錄也照這樣做，並補上舊的紀錄
- 會被一直呼叫的寫入 API（例如登入紀錄）要防灌：同一個 session 只記一次、每小時有上限，清舊資料只在真的寫入時做

## 破壞性操作要重新驗證

- 刪除帳戶、後台刪除使用者，要求最近 10 分鐘內登入過（看 JWT 的 `amr` 時間），否則回 `reauth_required`，網站與 App 重新跑一次 Google 登入再試
- 之後新增同等級的操作（例如轉移網站擁有者、清空所有資料）也套用這條

## 加密與託管

- 金鑰加密：PBKDF2-SHA256 600,000 次 → AES-GCM-256，都在裝置上做；從伺服器讀回的加密設定要檢查格式（`v = 1`、次數 600,000～5,000,000），不合就停下來，不要照跑
- 託管：設定或變更加密密碼時，一定要用團隊公鑰產生託管密文（`esc:v1:`）一起送出；解鎖成功後，如果伺服器說缺少就補上，失敗不能擋住解鎖
- 託管格式與工具在 `scripts/escrow.mjs`，網站、App 的實作都要能被它解開
- 團隊私鑰只離線保存，不進任何專案、雲端、聊天紀錄；公鑰放在網站 `src/config/escrow.ts` 與 App 的設定，換金鑰時兩邊一起換
- 從加密群組把驗證碼複製到沒加密的群組時，要先跳出確認，說明會以未加密方式存放
- 改到加密的行為時，網站、App 的說明文字與隱私權政策一起改，不能寫「我們無法還原」這種和實際不符的話

## 使用者輸入

- 圖片只能上傳（伺服器用 sharp 轉成 WebP、去掉中繼資料）或使用 Google 頭像，不接受任意網址；圖片透過網站的 `/media/` 提供，資料庫與程式碼不寫死 Supabase 網址
- 每個寫入都要有上限：筆數、名稱長度、金鑰長度、檔案大小、上傳次數
- 匯入時一筆壞掉不能讓整批失敗：其他照常匯入，最後告訴使用者哪幾行、為什麼讀不到
- 不使用 `dangerouslySetInnerHTML`；網址參數、錯誤說明這類外部文字不直接顯示，改成依代碼對應固定的中文訊息
- 錯誤訊息只回固定的中文說明，不把資料庫或伺服器的內部錯誤傳給使用者
- 不相信使用者送來的 IP 標頭；目前只信任 Vercel 設定的 `x-real-ip`，換主機時要重新檢查

## 通知與推播

- 通知的標題與內文只寫誰、哪個群組、做了什麼；不放驗證碼、金鑰、封鎖原因、IP、email（名稱用「名稱 → @ID → 一位使用者」）。推播會經過 Google 與裝置的通知中心，當成公開的文字看待
- 標題與內文由資料庫產生，網站與 App 直接顯示，不各自組字；連結只能是站內路徑（`/` 開頭，不能是 `//`、不能有反斜線與空白）
- 自己做的動作不通知自己（新的登入、金鑰加密密碼變更除外）；會被一直觸發的通知要合併或有上限（同一位操作者、同一種、同一位收件人一小時 30 則）
- 新增一種通知時，一起改：`notification_defaults()`（類別、預設、能不能關）、`docs/groups-and-permissions.md` 的事件表、網站與 App 的「通知」設定分頁與文字
- 推播 token 只能透過 `register_push_token` 寫到目前的 session；登出前要清掉；session 不在了 token 就不能再用
- 資料庫呼叫外部服務（pg_net）一律非同步、包 `exception`，失敗不能擋住原本的操作；沒有 pg_net、Vault、pg_cron 的環境要能照常跑
- Edge Function 的 secret（`FCM_SERVICE_ACCOUNT`）只放在 Supabase 的 Edge Function Secrets；Vault 的 `project_url`、`push_webhook_secret` 只在資料庫裡，都不進 git

## 機密

- Supabase 網址、anon key、service role key、Firebase 服務帳戶、Android keystore、託管私鑰都不進 git，也不印出來
- 網站有 CSP；新增外部來源（字型、圖片、API）時要一起更新

## 網站與 App 一致

- 功能與檢查兩邊一起做，行為、文字、錯誤訊息一致；只做一邊的話要在 commit 說明裡寫清楚
- 舊版 App 還會連線好一陣子：RPC 改簽名時保留預設值相容舊的呼叫方式，欄位限制用「忽略」而不是「報錯」

## 資料庫變更流程

1. 改 `database/init.sql`（新安裝用的完整結構），同時寫 `supabase/migrations/00xx_*.sql`（已上線的資料庫要跑的變更，包在 `begin; ... commit;`）
2. 用 PGlite 比對兩者結果一致，再跑功能測試（各種身分呼叫 RPC 的情境），新功能要加測試情境
   - 比對會看函式本體（`pg_get_functiondef`），migration 裡的 `create or replace function` 要和 init.sql 逐字一樣；從 init.sql 複製，不要手打
   - migration 要能重複執行（`if not exists`、`drop trigger if exists`、種子資料 `on conflict do nothing`），也要比對「跑兩次」的結果
   - 用到 Supabase 才有的東西（pg_net、Vault、pg_cron）時，用 `do` 區塊或 `execute` 加 `to_regclass` 判斷，PGlite 與正式環境都要能跑
3. migration 交給擁有者在 Supabase SQL Editor 執行，確認跑過才發布用到它的網站與 App

## 有變更就同步更新的文件

- 蒐集新的資料、改變用途或保存期限：隱私權政策（`src/app/privacy`）、刪除帳戶頁（`src/app/delete-account`）、Google Play 資料安全性表單
- 權限或群組行為：`docs/groups-and-permissions.md`
- 新的規則或踩到的坑：補進這份文件
